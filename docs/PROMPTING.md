# Промпт и контроль фактов

## Задача промпта

Модель получает не свободное задание «напиши продающий текст», а узкий редакционный контракт: превратить уже предоставленные факты в понятный черновик карточки. Техническая полнота определяется входом, а не знаниями модели.

## Два сообщения

### System instructions

Системный промпт задаёт роль и ограничения:

- входной JSON — единственный источник фактов;
- внешние знания и предположения запрещены;
- обозначения моделей, диапазоны, единицы и остальные значения с цифрами копируются дословно;
- цены, гарантии, сроки, сертификаты, страна, комплектация и наличие запрещены, если их нет во входе;
- отсутствие факта обозначается как «данных нет»;
- отдельно заданы длины, число поисковых запросов и назначение commercial-блока.

Полный текст находится в `src/product_copywriter/prompts.py` и версионируется вместе с кодом и тестами.

### User input

Второе сообщение содержит только инструкцию считать JSON единственным источником и сериализованный `ProductInput`. Сортировка ключей делает запрос воспроизводимым и удобным для отладки.

## Почему Structured Outputs

В Responses API передаётся JSON Schema модели `GeneratedCopy` со `strict=true`. Модель может вернуть только четыре редакционных поля:

- `seo_title`;
- `seo_description`;
- `search_queries`;
- `commercial_block`.

Ограничения длины и количества входят в схему. Технический список характеристик отсутствует в ответе модели намеренно.

## Defense in depth

Промпт сам по себе не является гарантией, поэтому после API работают кодовые проверки:

1. Pydantic отклоняет лишние поля, короткое/длинное описание и неверное число запросов.
2. `ProductCardService` копирует `specs` во входном порядке и подставляет «данных нет» для пустого списка.
3. Grounding-нормализатор приводит варианты дефиса к одному виду и извлекает все токены с цифрами из редакционного текста.
4. Каждый такой токен должен присутствовать во входе; для семейства модели допускается только буквенно-цифровой префикс перед дефисом исходного артикула, например `МК110` из `МК110-224.8Д.4Р`.
5. При несовпадении карточка не возвращается, а CLI завершает работу с отдельным кодом ошибки.

## Почему не просим модель генерировать характеристики

Перефразирование допустимо для SEO-текста, но вредно для технических таблиц: может измениться единица, диапазон или модификация. Детерминированный перенос характеристик проще, надёжнее и удобнее для проверки контент-менеджером.

## Обработка неполного входа

`name` обязателен, потому что без него нельзя идентифицировать карточку. Остальные поля допускают отсутствие:

- пустой `manufacturer` становится «данных нет»;
- пустой `specs` превращается в одну явную строку «Ключевые характеристики: данных нет»;
- все пропуски перечисляются в `missing_fields` и в Markdown-разделе «Требуют уточнения».

Модель не получает разрешения заполнить эти пробелы самостоятельно.

## Наблюдаемые ограничения

- Проверка цифровых токенов не заменяет фактчекинг общего текста.
- Записанные словами числа требуют отдельного лингвистического анализатора.
- Модель может сформулировать слишком общее преимущество без цифр; такой текст должен проверить человек.
- При очень бедном входе выдержать 800-1200 полезных символов без повторов сложно. В production-варианте разумно добавить режим «недостаточно данных» до вызова API.

## Как развивать решение

- добавить eval-набор с намеренными провокациями на галлюцинации;
- привязывать каждое предложение к одному или нескольким входным полям;
- сравнивать сущности и единицы, а не только токены;
- добавить повторную генерацию с обратной связью о конкретном нарушении;
- сохранять версию промпта и модели рядом с черновиком для аудита.
