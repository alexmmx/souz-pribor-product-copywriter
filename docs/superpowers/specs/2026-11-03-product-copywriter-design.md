# AI-помощник для товарных описаний - дизайн

## Назначение

Локальный Python-сервис принимает JSON с данными контрольно-измерительного прибора и создаёт готовый к копированию черновик карточки B2B-товара. Решение должно показать практическую работу с LLM API, качественный промпт и техническую защиту от выдуманных характеристик.

## Цели

- Принимать один товар или список товаров из JSON-файла.
- Генерировать SEO-заголовок до 70 символов, SEO-описание 800-1200 символов, 3-5 поисковых запросов и commercial-блок.
- Возвращать Markdown или JSON.
- Явно перечислять отсутствующие необязательные поля.
- Никогда не добавлять технические значения, которых нет во входе.
- Давать понятные ошибки для некорректного JSON, пустого названия, конфигурации и OpenAI API.
- Поставляться с двумя примерами из каталога СОЮЗ-ПРИБОР, тестами и русскоязычным README.

## Не входит в работу

- CMS, база данных, авторизация, админ-панель и деплой.
- Автоматический парсинг всего YML-фида при каждом запуске.
- Проверка фактов по внешним источникам во время генерации.
- Автоматическая публикация карточек в интернет-магазине.

## Ограничения и защита от ошибок

- Python 3.11+; OpenAI Responses API; ключ только в переменной окружения или игнорируемом `.env.local`.
- В запрос API передаётся только пользовательский JSON, запрос выполняется без хранения ответа (`store=false`).
- Structured Outputs ограничивает форму ответа JSON Schema.
- Список характеристик не доверяется модели: сервис строит его детерминированно из `specs`.
- После генерации сервис проверяет длины, число запросов и каждое токенизированное значение с цифрами. Значение, которого нет во входных данных, блокирует результат как риск галлюцинации.
- Модель получает прямой запрет на внешние знания, цены, гарантии, сроки, сертификаты и неподтверждённые преимущества.

## Выбранный подход

### Рассмотренные варианты

1. **CLI + OpenAI Structured Outputs - выбран.** Минимум инфраструктуры, простой запуск и удобная автоматизация. Валидация и защита от галлюцинаций остаются в коде, а не только в промпте.
2. Простая веб-форма. Нагляднее на демонстрации, но добавляет HTTP/UI-слой, который не влияет на главные критерии ТЗ и увеличивает объём MVP.
3. Только скрипт с текстовым ответом модели. Быстрее всего, но слабее обрабатывает ошибки, формат и выдуманные характеристики.

Выбран первый вариант как наиболее убедительный для ограничения 2-4 часа: он покрывает все обязательные требования и оставляет веб-интерфейс очевидным следующим шагом.

## Архитектура

- `models.py`: Pydantic-модели входа, черновика модели и итоговой карточки.
- `input_loader.py`: безопасное чтение JSON-объекта или массива.
- `prompts.py`: версия системного промпта и сериализация входного контекста.
- `provider.py`: адаптер OpenAI Responses API и перевод внешних ошибок в ошибки приложения.
- `service.py`: оркестрация, детерминированные характеристики, список пропусков и grounding-проверка.
- `renderers.py`: Markdown и JSON для копирования.
- `cli.py`: аргументы, загрузка `.env.local`, коды завершения и сообщения пользователю.

Провайдер возвращает только текстовые поля модели. `ProductCardService` добавляет характеристики из исходного `specs`, вычисляет отсутствующие поля и отклоняет неподтверждённые цифровые значения до показа результата.

## Интерфейс

```text
product-copywriter examples/input/products.json --format markdown
product-copywriter product.json --format json --output result.json
```

Вход допускает один JSON-объект либо массив объектов. `name` обязателен и не может быть пустым. `manufacturer`, `specs`, `description` и `source_url` допускают отсутствие; итог явно перечисляет пропуски.

## Проверка готовности

- Unit-тесты: вход, доменные ограничения, промпт, OpenAI request shape, ошибки API, grounding и renderers.
- CLI integration: валидный файл, неверный JSON, отсутствующий ключ и запись результата.
- Один реальный API-запуск для двух примеров.
- Ruff, pytest, `bitrix-vibe test-plan`, `bitrix-vibe verify`, `bitrix-vibe health`.
