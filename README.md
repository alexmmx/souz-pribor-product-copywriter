# AI-помощник для подготовки товарных описаний

Локальный Python-прототип для контент-менеджера B2B-интернет-магазина. Сервис получает данные о приборе в JSON, обращается к OpenAI Responses API и возвращает проверенный черновик карточки в Markdown или JSON.

Главный принцип решения: **модель отвечает за редакционный текст, а код — за технические факты**. Характеристики переносятся в результат напрямую из входного JSON, а любое новое цифровое значение в сгенерированном тексте блокирует выдачу.

## Что реализовано

- один товар или массив товаров в JSON;
- SEO-заголовок до 70 символов;
- SEO-описание длиной 800-1200 символов;
- структурированный список характеристик;
- 3-5 поисковых запросов;
- commercial-блок для менеджера;
- явный список отсутствующих полей;
- вывод в Markdown или JSON;
- Structured Outputs через OpenAI Responses API;
- обработка неверного JSON, пустых полей, отказа модели, таймаута, лимитов и HTTP-ошибок;
- атомарная запись результата: существующий файл не портится при сбое;
- 46 автоматических тестов, включая проверку сохранённых live-snapshots.

## Быстрый старт

Требования: Python 3.11+ и [uv](https://docs.astral.sh/uv/).

```bash
git clone https://github.com/alexmmx/souz-pribor-product-copywriter.git
cd souz-pribor-product-copywriter
uv sync
cp .env.example .env.local
```

Добавьте API-ключ в локальный `.env.local`:

```dotenv
OPENAI_API_KEY=your-key-here
OPENAI_MODEL=gpt-6.1-sol
```

`.env.local` исключён из Git. Ключ не передаётся в аргументах команд и не хранится в коде.

Сгенерировать Markdown в терминал:

```bash
uv run product-copywriter examples/input/products.json
```

Сохранить JSON:

```bash
uv run product-copywriter examples/input/products.json \
  --format json \
  --output result.json
```

Выбрать другую доступную модель:

```bash
uv run product-copywriter product.json --model gpt-6-luna
```

## Формат входных данных

Сервис принимает один объект или массив объектов:

```json
{
  "name": "ПМ01-24.АВ",
  "manufacturer": "ОВЕН",
  "specs": {
    "Тип прибора": "GSM/GPRS-модем",
    "Диапазон напряжений питания постоянного тока": "от 10 до 30 В",
    "Интерфейс связи": "RS-232/RS-485"
  },
  "description": "GSM/GPRS-модем для удалённого обмена данными...",
  "source_url": "https://www.souz-pribor.ru/product/pm01-24-av/"
}
```

`name` обязателен. Если `manufacturer`, `specs` или `description` отсутствуют, сервис продолжает работу, помечает поле как требующее уточнения и не пытается восстановить факт из знаний модели.

Для демонстрации выбраны два товара из [YML-каталога СОЮЗ-ПРИБОР](https://www.souz-pribor.ru/yml/any/feed.xml):

Файлы:

- [`examples/input/products.json`](examples/input/products.json) — проверенные входные данные;
- [`examples/output/products.md`](examples/output/products.md) — результат для копирования;
- [`examples/output/products.json`](examples/output/products.json) — структурированный результат.

Текущие snapshots в `examples/output/` получены реальными запросами к OpenAI Responses API 3 ноября 2026 года. После получения они прошли те же Pydantic-модели и grounding-проверку, что используются сервисом. Метрики и сценарии проверки зафиксированы в [`docs/LIVE_TESTS.md`](docs/LIVE_TESTS.md). Для повторной live-генерации нужен OpenAI API-ключ с доступной квотой.

## Как предотвращаются выдуманные характеристики

Защита состоит из нескольких независимых слоёв:

1. Системный промпт объявляет входной JSON единственным источником фактов.
2. Модель обязана копировать значения с цифрами и единицами дословно.
3. Structured Outputs фиксирует форму ответа и ограничения длины.
4. `characteristics` вообще не генерируются моделью — сервис строит их из входного `specs`.
5. Post-validation сравнивает каждое цифровое обозначение результата с входом. Новое значение, модель или диапазон вызывает ошибку и не показывается пользователю.

Подробности и принятые решения: [`docs/PROMPTING.md`](docs/PROMPTING.md).

## Ошибки и коды завершения

| Код | Причина |
| ---: | --- |
| 0 | Успешная генерация |
| 2 | Файл или входной JSON некорректен |
| 3 | Не настроен API-ключ или модель |
| 4 | Ошибка/отказ OpenAI API |
| 5 | Обнаружено неподтверждённое цифровое значение |
| 6 | Не удалось записать выходной файл |

Сообщения предназначены для пользователя и не содержат traceback, API-ответов или секретов.

## Принятые решения

- **CLI вместо веб-интерфейса.** Он покрывает обязательный вариант приёма JSON и сохраняет MVP в рамках 2-4 часов.
- **Responses API + Structured Outputs.** Схема ответа проверяется до бизнес-логики; запросы выполняются с `store=False`.
- **`gpt-6.1-sol` по умолчанию.** Модель можно заменить через `OPENAI_MODEL` или `--model` без изменения кода.
- **Последовательная batch-обработка.** Результат публикуется только после успеха всех товаров.
- **Человеческая проверка обязательна.** Выход — черновик, а не автоматическая публикация.

## Ограничения и возможные улучшения

- Grounding-правило надёжно блокирует новые значения с цифрами, но не доказывает семантическую истинность каждого общего утверждения и не распознаёт все числа, записанные словами.
- Качество результата зависит от полноты и корректности входа; сервис не сверяет паспорт с внешними источниками.
- Нет retry/backoff поверх retry-механизма SDK, очереди, кэша и параллельной batch-обработки.
- Нет веб-формы, истории версий и интеграции с CMS.
- Следующие шаги: набор eval-кейсов контент-менеджера, построчные ссылки на источник, UI предпросмотра, ручное подтверждение и экспорт в CMS.

## Структура проекта

```text
src/product_copywriter/
  cli.py           # аргументы, коды ошибок, атомарная запись
  input_loader.py  # JSON -> ProductInput
  models.py        # Pydantic-контракты
  prompts.py       # системный промпт и входное сообщение
  provider.py      # OpenAI Responses API
  renderers.py     # Markdown и JSON
  service.py       # оркестрация и grounding
tests/             # unit и CLI integration tests
examples/          # два входа и два формата результата
```
